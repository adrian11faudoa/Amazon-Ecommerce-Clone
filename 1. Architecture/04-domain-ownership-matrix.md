# Domain Ownership Matrix

This matrix is normative. No module, service, or client may write data outside its authoritative ownership. Reads from other domains happen only via the "Allowed Integration Mechanism" column.

| Data Category | Authoritative Owner | Read Consumers | Write Consumers | Allowed Integration Mechanism | Forbidden Access Pattern | Consistency Expectation |
|---|---|---|---|---|---|---|
| Credentials, sessions, tokens | Identity & Access | All domains (via `AuthContext`) | Identity & Access only | In-process auth service call / JWT validation | Any domain querying `User`/`Credential` tables directly | Strong |
| Customer profile, addresses, wishlist | Customer | Checkout, Order (snapshot), Notification | Customer only | Service call / event (`CustomerProfileUpdated`) | Order storing a live FK to `Address` instead of a snapshot | Strong (mutation), snapshot semantics downstream |
| Seller org, staff roles, verification, storefront | Seller | Catalog, Payment (Connect linkage), Administration | Seller, Administration (verification approval) | Service call / event | Catalog writing seller status directly | Strong |
| Category, Product, Variant, SKU, Attributes | Catalog | Search, Cart, Checkout, Inventory (keyed reference), Review | Catalog, Moderation (force-unpublish via command) | Service call / event (`ProductPublished`, etc.) | Search or Cart writing back to Catalog tables | Strong (writes), eventually consistent projection to Search |
| Price | Pricing & Promotion | Cart (display), Checkout (authoritative re-read), Catalog (display), Search | Pricing & Promotion only | Service call / event (`PriceChanged`) | Cart caching a price and treating it as authoritative at order time | Strong; checkout never trusts a cached price |
| Promotions, coupons | Pricing & Promotion | Checkout | Pricing & Promotion, Administration (platform-level promos) | Service call | Checkout computing discount logic itself | Strong |
| Inventory quantities, reservations | Inventory | Cart (soft check), Checkout (hard reserve), Order (commit), Fulfillment (decrement), Return (restock) | Inventory only (via commands invoked by Checkout/Fulfillment/Return) | Service call within same transaction boundary as the invoking domain's step; events for downstream notification | Fulfillment updating quantity columns directly instead of calling `CommitReservation`/`AdjustInventory` | Strong — single source of truth for overselling prevention |
| Cart, cart items | Cart | Checkout (consumes at session start) | Cart only | Service call | Checkout mutating Cart after session starts (Checkout owns its own snapshot from that point) | Strong, low-stakes |
| Checkout session state | Checkout | Order (reads once, at completion) | Checkout only | Internal orchestration | Any domain other than Checkout transitioning `CheckoutSession` state | Strong per step, saga-style overall |
| Order, order items | Order | Payment, Fulfillment, Review, Notification, Analytics | Order (creation via Checkout only), no in-place edits post-creation | Service call / event (`OrderCreated`) | Payment or Fulfillment rewriting `OrderItem` snapshot fields | Strong at creation; immutable thereafter |
| Payment, refund records | Payment | Order (status projection), Administration | Payment only (webhook-driven + admin-initiated refund command) | Service call / verified webhook / event (`PaymentCaptured`) | Order or Checkout writing payment status directly | Strong locally; eventually consistent with provider, reconciled |
| Shipment, return records | Fulfillment & Shipping | Order (status projection), Inventory (restock trigger), Notification, Review (eligibility) | Fulfillment & Shipping only | Service call / verified webhook / event | Inventory reading shipment table directly instead of consuming `ShipmentDelivered`/`ReturnReceived` events | Strong per transition |
| Reviews | Review | Catalog (aggregate display), Search, Moderation | Review (submission), Moderation (removal via command) | Service call / event | Catalog writing review rows | Strong; aggregate recompute eventually consistent |
| Notification preferences, delivery log | Notification | (terminal — no downstream consumers of raw log) | Notification only | Event consumption from all domains | Any domain reading another customer's notification log for non-notification purposes | Eventually consistent, at-least-once |
| Media asset metadata | Media | Catalog, Review, Seller (reference by asset ID) | Media only | Service call / event (`MediaProcessed`) | Catalog storing raw S3 keys instead of `MediaAsset` references | Strong metadata, async derived variants |
| Search index documents | Search | Web/Mobile (via API), Catalog (read-only for reindex triggers) | Search only (via indexing pipeline, never direct client writes) | Async projection from Catalog/Pricing/Inventory/Review events | Any write path treating OpenSearch as authoritative | Eventually consistent, bounded lag |
| Audit log | Administration | Administration, Security/Compliance review | Every domain writes its own audit entries via a shared audit-logging service interface (single logical owner: Administration schema), never a foreign domain's row-level table | Shared logging service call, co-transactional with the audited action | Any domain bypassing the audit service to write raw log tables | Strong, co-transactional |
| Moderation cases, content flags | Moderation | Catalog, Review (status effect only) | Moderation only | Service call / command to Catalog/Review (`ForceUnpublish`, `RemoveReview`) | Moderation directly updating `Product.status` column | Strong |
| Risk signals, abuse cases | Fraud & Abuse | Checkout (synchronous gate, read-only), Administration | Fraud & Abuse only | Service call (bounded-timeout) / event | Checkout persisting its own risk score | Strong for case record; scores may be probabilistic/derived |
| Analytics events/aggregates | Analytics | Administration (dashboards), external BI sink | Analytics only (via event ingestion) | Async event consumption | Analytics writing back to any transactional table | Eventually consistent, reconstructable |

## Reconciliation Rule

If two domains appear to need authority over the same fact (e.g., "is this product available"), the fact is decomposed: Catalog owns *existence/publish state*, Inventory owns *quantity availability*, Pricing owns *sellability at a price point*. No single "availability" flag is jointly owned — each contributing domain owns its slice and downstream consumers (Cart, Search) combine the slices for display, never write back a combined flag as new authoritative state.
